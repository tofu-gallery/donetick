# Tofu gallery copy

This repository is Tofu's copy of **donetick/donetick** (licence: AGPL-3.0), listed in Tofu's app gallery as **Shared chore chart**: Donetick, a chore and task tracker for a household or a small group, with repeating schedules, assignees who take turns, points and rewards, labels, projects and a calendar.

- `develop` mirrors the upstream repository and is never committed to by Tofu.
- `tofu` carries Tofu's own changes; tags named `pin/<date>` (`pin/<date>.<n>` for a later pin made the same day) mark the versions the gallery points to. The current pin is `pin/2026-10-26`. The earlier pins, `pin/2026-10-25`, `pin/2026-10-25.1` and `pin/2026-10-25.2`, stay where they are.
- A visitor who chooses this app gets a private snapshot of the pinned version in their own Tofu account. Their copy does not follow upstream updates, or later pins.
- Upstream, server: https://github.com/donetick/donetick at v0.1.83, `549e44c836de6b54f026624ccce9d6e8df726a30` (2026-10-18), the latest stable release. `tofu` starts from that tag, which is on `develop`.
- Upstream, web app: https://github.com/donetick/frontend at `0a0850a734752fcdf50513c033ec5159a9a79821` (2026-10-18, app version 1.2.58), in `web/`. Upstream's release workflow builds the frontend's default branch into the server at release time; this is that branch's head when v0.1.83 was released, going by commit times (the next frontend commit is from 2026-10-19). It was not compared with the published v0.1.83 image.
- Why not `develop`'s head: at the time of the first pin, `develop` (`584301c`, tagged v0.1.84-beta.3) does not compile (`internal/notifier/push/push.go:99: not enough return values`), and upstream published no release for that tag.

## How Tofu runs it

- Framework preset `container`, root folder: the repository root. Tofu builds the root `Dockerfile` and runs the image as a service, so there is no separate install command, build command or output directory.
- The `Dockerfile` has three stages:
  1. `node:22-bookworm-slim` builds the web app in `web/`: `npm ci --ignore-scripts --no-audit --no-fund`, `npx --no-install patch-package`, then `npx --no-install vite build --mode selfhosted` with `VITE_APP_API_URL=""` (the API is the same server) and `VITE_IS_SELF_HOSTED=true`.
  2. `golang:1.24-alpine` downloads and verifies the Go modules, replaces the placeholder `frontend/dist` with the web app built in stage 1, and builds the server with `CGO_ENABLED=0 go build`. The server embeds `frontend/dist` (`go:embed`) and serves it.
  3. `alpine` runs `/donetick` through `/bin/sh /tofu-entrypoint.sh`, as root (the image has no `USER` line), with `/config/selfhosted.yaml` (see below) and `DT_ENV=selfhosted`. Nothing in the build or the start runs a file of this repository directly, so files that arrive without their execute bit work the same.
- Database: PostgreSQL, the app's Tofu database, read from `DATABASE_URL`. Without `DATABASE_URL`, Donetick uses SQLite (`donetick.db` in the working directory), which is lost on every restart.
- Migrations: the server makes and updates its own tables at every start, before it starts listening: GORM's AutoMigrate, then Donetick's data migrations (recorded in the `migrations` table), then the SQL files in `internal/database/migrations` (recorded in `gorp_migrations`), then row-level security on each of its 41 tables. On PostgreSQL all of it is one transaction under an advisory lock, so that several starts at the same moment take turns (see "Start-up when several starts run at once"). There is no `supabase/migrations` folder, so Tofu applies no SQL of its own.
- Settings Tofu sets: `PORT`, and with the app's managed database `DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_CA_CERT`. Donetick reads `PORT` and `DATABASE_URL` (through `tofu-entrypoint.sh` and `internal/database/database.go`); it does not read the three Supabase settings. Settings the image sets: `DT_ENV=selfhosted`, `DT_SOURCE_URL` (this pin's source) and, in `/config/selfhosted.yaml`, the upload limits (see "Files"). Settings a gallery copy saves before its first deploy: `DT_SERVER_PUBLIC_HOST` and `DT_EMAIL_APP_HOST`, both the copy's own address, and `DT_SOURCE_URL`, this pin's exact source. Nothing has to be typed by hand.
- Settings an owner may add later: `DT_IS_USER_CREATION_DISABLED=true` to close sign-up (see "Accounts"), `DT_JWT_SECRET` as a hidden value (see "The sign-in secret"), the `DT_STORAGE_*` settings for a storage bucket, two of them hidden values (see "Files"), the `DT_EMAIL_*` settings for an SMTP server, and `DT_TELEGRAM_TOKEN` or `DT_PUSHOVER_TOKEN` for notifications (Discord notifications use a webhook set inside the app). Every setting of Donetick's configuration (`config/config.go`) can be set as `DT_` plus its path in capitals with `_` for `.`, for example `DT_SERVER_RATE_LIMIT`, whether or not `/config/selfhosted.yaml` lists it, and such a setting wins over the file.

## Start-up when several starts run at once

Tofu's container hosting can start a new deployment several times within a second or two, each container knowing nothing of the others. Upstream's start-up then races on an empty database: started five times at the same instant (the test below), the previous pin left one server answering and four exited with `panic: ... relation "storage_usages" does not exist` or `duplicate key value violates unique constraint "gorp_migrations_pkey"`, after AutoMigrate had failed with `relation "users" already exists` and duplicate `pg_type` entries. A start that crashes answers nothing, and Tofu refuses a first deployment whose home page does not answer.

- **Where the lock is.** `database.StartupSchema` in `internal/database/tofu_startup_schema.go`, called from `main.go` before the server starts listening. On PostgreSQL the whole schema step is ONE transaction on the server's own connection (`DATABASE_URL`), whose first statements are `SET LOCAL lock_timeout = '180000ms'` and `SELECT pg_advisory_xact_lock(7237970109966541675)`, a fixed key ("donetick" in ASCII) that every start uses. One start does the work while the others wait; each of them then takes the lock in turn and reads the schema's state inside the lock instead of assuming anything about it.
- **Why it holds through Tofu's pooler.** `DATABASE_URL` goes through a transaction pooler (port 6543), which keeps one server connection for a transaction from `BEGIN` to its end and hands it to other clients only between transactions. A transaction-level advisory lock lasts exactly as long as that transaction, so the lock, the work and the commit all happen on that one server connection, and the lock ends with the transaction, also when a start dies half-way and its transaction is rolled back. A session-level lock (`pg_advisory_lock`) would not be safe there. DDL is transactional in PostgreSQL, so no start sees half a schema, and a failed step leaves the database as it was.
- **Bounded waits.** A start waits at most 3 minutes for the lock and then fails, and the hosting starts it again; the same bound applies to the step's own waits for table locks. A start that still meets a duplicate-object error, from something that does not take the lock (an older version of the app, say) changing the schema at the same moment, runs the whole step once more.
- **What the step does.** AutoMigrate; then the data migrations, inside a savepoint: a failing one is undone, logged and left unrecorded, and the server goes on, as upstream; then the SQL files of `internal/database/migrations`, split into statements by sql-migrate's own parser and recorded in its `gorp_migrations` table as before, now in the same transaction (upstream ran sql-migrate twice in a row; the second run found nothing). A failing AutoMigrate or SQL file now stops the start, with the database as it was; upstream ignored AutoMigrate's error and went on with half a schema. SQLite keeps upstream's steps unchanged.
- **A later start is quick.** The step ends by writing a comment on the `migrations` table naming the SHA-256 of the server's own executable. A start of the same build that finds it under the lock skips AutoMigrate, the data migrations and the SQL files and only checks row-level security; any other build, and an empty database, runs the whole step. So the starts that wait behind the first one, and every restart of the same version, take a fraction of a second. A schema changed by hand afterwards is not repaired until a new build starts; upstream's AutoMigrate added missing tables and columns back at every start.
- **Row-level security.** Tofu's databases made before 2026-10-30, every one today, grant each new table in `public` to the Data API's roles `anon` and `authenticated` through PostgreSQL's default privileges, and a live copy of the previous pin had all 41 of Donetick's tables open to anyone holding the project's public key, `users` with its password hashes and `user_sessions` among them. Every start now turns row-level security on, in the same locked transaction and only where it is off, for every table the app makes: the 40 tables of the models AutoMigrate creates (the data migrations' `migrations` among them) and sql-migrate's `gorp_migrations`, 41 in all, in one round trip, and only tables the server's role owns. There are no policies: `anon` and `authenticated` get no row and cannot write one, while the server's own connection, which owns the tables, is not limited by it. A table that is not one of Donetick's own is not touched.
- **How many statements.** On an empty database the first start sends 255 statements to the database (the previous pin: 278) and answered `GET /` with 200 after 0.3 s here. Through a stand-in for the network that adds 20 ms to every round trip, the first start took 6.8 s (previous pin: 7.1 s), and a later start of the same build 0.5 s with 17 statements, where the previous pin's later start sent 718 and took 18 s.
- **What the five-starts test showed.** On a scratch PostgreSQL 14 with the roles `anon`, `authenticated` and `service_role` and the same default privileges as today's Tofu databases, five copies of the server, each in its own folder on its own port, were started at the same instant with one `DATABASE_URL` to an empty database. The previous pin: one answered and four exited (above); all 41 tables had row-level security off, `anon` read the rows of `migrations` and `gorp_migrations`, and an empty row from `anon` went into 18 tables (the other 23 refused it only for a missing value or a foreign key). This pin, three times, on a new database each time: all five answered `GET /` with 200 within 1.4 s, none exited, and no log said "already exists", "duplicate" or "panic"; one start did the step and four found it done after waiting 0.1 to 0.2 s for the lock; all 41 tables had row-level security on, and as `anon` `SELECT 1 FROM <table> LIMIT 1` returned no row and an `INSERT` was refused (`42501`, row-level security) on every one. Five starts on a database the previous pin had made, and on the one its race had left behind, ended the same way: one start brought the schema up to date and closed the 41 tables, and four found it done.

## Files: attachments, images and profile photos

Donetick keeps uploaded files (attachments, images in task descriptions and completion notes, profile photos) in an S3-compatible storage bucket, such as Amazon S3, Cloudflare R2 or MinIO. A copy has none until its owner adds one, and Tofu's hosting keeps no files on the app's own disk between restarts.

- Until then, uploading a file answers: "Uploading files is not set up yet: the owner of this app has to add a storage bucket with the DT_STORAGE_* settings (see TOFU.md in the app's source code)." Everything else works without a bucket.
- To add one: make a bucket and an access key that can read, write and delete objects in it, save the settings below on the app's Keys & settings page (the access key's id and secret as hidden values), and deploy again; the server reads them when it starts. Each setting was checked against a local stand-in for S3 (see "Verification"); a real storage service was not tried.

| Setting | What it is |
|---|---|
| `DT_STORAGE_BUCKET_NAME` | The bucket's name. Required. |
| `DT_STORAGE_REGION` | The bucket's region, for example `us-east-1`; Cloudflare R2 takes `auto`. Required: without it the S3 client refuses every request. |
| `DT_STORAGE_ACCESS_KEY` | The access key's id. Required; a hidden value. |
| `DT_STORAGE_SECRET_KEY` | The access key's secret. Required; a hidden value. |
| `DT_STORAGE_ENDPOINT` | The S3 address of a service other than Amazon S3, for example `https://<account id>.r2.cloudflarestorage.com` for Cloudflare R2. Leave it unset for Amazon S3. |
| `DT_STORAGE_PATH_STYLE` | `true` for a service that wants the bucket's name in the address's path instead of its host name, such as MinIO. |
| `DT_STORAGE_BASE_PATH` | A folder in the bucket that the files go under, for example `donetick`. Recommended: without it a profile photo's address on `DT_STORAGE_PUBLIC_BUCKET_HOST` has a double slash (`https://<host>//profiles/...`). Choose it once: files are looked up under it, so the ones saved before a change can no longer be shown or deleted. |
| `DT_STORAGE_PUBLIC_BUCKET_NAME` | Optional: a separate bucket for profile photos. Without it they go to `DT_STORAGE_BUCKET_NAME`. |
| `DT_STORAGE_PUBLIC_BUCKET_HOST` | Optional: the host name, without `https://`, where the profile photos' bucket can be read by anyone, such as a public custom domain on it. Without it a profile photo's address is a signed link that stops working 7 days after the upload (from the code; not waited for), and the photo has to be uploaded again. |
| `DT_STORAGE_MAX_FILE_SIZE` | The largest attachment or image, in bytes. The image sets 4194304 (4 MiB). A larger file is refused, and every place in the web app that uploads one says "File Too Large". |
| `DT_STORAGE_MAX_USER_STORAGE` | The bytes of attachments and images all members of one circle (household) can keep together. The image sets 1073741824 (1 GiB). Past it an upload is refused, and the web app says "Storage Quota Exceeded". |

- Profile photos count toward neither limit, as upstream has it: the server checks no size for them (the web app shrinks each to 160 × 160 pixels before uploading it), they are not added to the circle's storage, and a replaced photo is not deleted from the bucket (checked against the stand-in, without a photo host). Someone who uploads photos through the API instead of the web app can therefore keep more in the bucket than the two limits say; closing sign-up (see "Accounts") limits who can.
- Attachments and images are shown through signed links to the bucket, which last 7 days and are made again when they run out. `DT_STORAGE_PUBLIC_HOST` puts another host name in those links (a CDN in front of the bucket) and `DT_STORAGE_PUBLIC_READ=true` leaves them unsigned, for a bucket anyone can read; both are optional and were not tried.
- The web app also keeps images in the browser for offline use, fetching them from the bucket. For that the bucket needs a CORS rule allowing `GET` from the copy's address; without one, images still show, and only the offline copy is missing.
- `DT_STORAGE_STORAGE_TYPE=local` keeps files on the container's own disk instead, which Tofu's hosting does not keep: every file is lost at the next restart or deploy.

## The sign-in secret

- Donetick signs its sign-in tokens with `DT_JWT_SECRET`, and also the links to files kept in local storage and the live-update connection's tokens. It refuses to start with a short or known-weak secret.
- On Tofu, when `DT_JWT_SECRET` is not set, `tofu-entrypoint.sh` sets it at each start to the SHA-256 of `donetick-jwt-secret:` followed by the whole `DATABASE_URL`, written as 64 hex characters. So a copy starts with nothing set by hand, and a restart keeps everyone signed in.
- Anything that changes `DATABASE_URL` changes the secret at the next start: a new database password, a different host, port or pooler address, other query options, or a database Tofu brings back under a different address. After that start, every sign-in token issued before is refused (`401`). The refresh tokens are random values stored hashed in the database, not signed with the secret, so a client holding one still gets a new sign-in token (checked through the API below; not checked in a browser).
- To keep the secret independent of the database address, set `DT_JWT_SECRET` as a hidden value on the app's Keys & settings page, at least 32 characters, for example the output of `openssl rand -base64 48`, and keep it unchanged afterwards. Setting it has the same effect as a change, once.
- The derived secret is only as secret as `DATABASE_URL`, which Tofu keeps as a hidden value.
- Without `DATABASE_URL` and without `DT_JWT_SECRET`, the entrypoint makes a random secret for that start only and says so in the log, as upstream does on a filesystem that keeps nothing.

## Accounts

- Donetick has its own accounts, not Tofu sign-in. Anyone who can open the address can sign up until the owner closes sign-up.
- There is no administrator of the whole app: every account that signs up gets its own circle (household) and is that circle's admin. Others join a circle with its invite code (Settings, Circle), and an account can also make sub-accounts for children.
- To close sign-up, set `DT_IS_USER_CREATION_DISABLED=true` and deploy again. The sign-in page then hides "Sign up", and the sign-up request gets `403`; existing accounts keep signing in. Make the owner's own account, and let the household sign up and join the circle, before closing it; or make the app private on Tofu.
- Password reset: no email server is set up, so a reset link is not emailed. It is printed in the app's runtime log (`=== PASSWORD RESET LINK ===`), starting with the copy's address (`DT_EMAIL_APP_HOST`). An owner who wants emails sets the `DT_EMAIL_*` settings for an SMTP server.

## What works differently on Tofu

- **Reminders are sent while the server runs.** The server checks every 3 minutes for notifications that have come due and sends those scheduled in the last 15 hours. A reminder that falls due while the app is asleep goes out at the first check after it wakes, if that is within 15 hours, and never after that. Notifications also need a channel the owner sets up: a Telegram or Pushover token, or a Discord webhook address entered in the app. Push notifications to the mobile apps need Firebase or Donetick Bridge, both off.
- **Files need the owner's bucket.** Until the owner adds one, uploads say so and nothing else changes (see "Files").
- **Live updates are optional.** Each browser can turn on "real-time updates" in Settings, which keeps a long-lived connection (server-sent events) open. Whether Tofu's hosting keeps such a connection open was not tested; without it, pages update when they are reloaded or refetched, as with the switch off.
- **Privacy Policy and Terms of Use** in the app's footers and pages are upstream's documents for the donetick.com service. They describe that service, not a copy run by its owner on Tofu.
- **Calendar feeds** (Settings, Calendar) give links on the copy's own address, `DT_SERVER_PUBLIC_HOST`; without it the server would name `http://localhost:2021`, its built-in default (from the code; not tried).
